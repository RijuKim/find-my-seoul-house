# Acceptance scenarios

## Success
1. 360px/1280px 앱에서 상단 거래 유형 토글이 보이고 44px 터치 타깃·키보드 포커스를 가진다. 기본은 매매이며 기존 결과가 완전히 그대로다(전월세 API 호출 0).
2. 매매↔전세 전환 시 결과·카드 수·지도 마커·정렬·평형/가격/구 필터가 새 거래 유형 기준으로 일관 갱신된다. 전세 모드에서 "전세 실거래(과거 신고)", "월세는 제외" 고지가 표시된다.
3. 전세 판정 fixtures: 월세0·보증금>0·비갱신 → 포함; 월세>0 → 제외; 보증금0/누락 → 제외; 갱신(useRRRight) → 제외. 보증금이 카드 가격으로 매핑된다.
4. 전세 예산: `jeonsePaymentAffordablePrincipal` 이자만 상환; 금리0이면 LTV 상한(보증금×financedShare)으로 유한 판정; 월 부담은 이자만. 매매 예산 경로는 불변.
5. 서버: `tradeType` 검증 enum; sale 경로 회귀 없음; jeonse 경로가 기존 배치/백오프/캐시 규약 준수; 캐시 키에 tradeType 포함; 오류 시 부분 결과+사유.
6. 라이브(키 존재): 특정 구 아파트 전세 실제 레코드 ≥1건(실응답 근거) 확보 및 문서 기록. 없으면 명시 스킵.
7. `pnpm check`/`test`/`build`/`build-api.mjs` 통과; 브라우저 360/1280 콘솔 에러 0·오버플로 없음.

## Anti-scenarios
1. 기본 매매 로드에서 전월세 API가 호출되거나 매매 결과가 달라진다(회귀).
2. 월세>0/보증금0/갱신 레코드가 전세로 포함되거나, 빈 결과를 샘플/추정으로 조용히 대체한다.
3. 전세 가격이 보증금이 아닌 다른 값(월세·매매가)으로 매핑되거나, 매매 원리금균등 공식이 전세에 사용된다.
4. 전세도 매매와 동일하게 LTV/예산이 계산되어 이자만 구조가 무시되거나, 금리0 전세가 무한대로 표시된다.
5. 거래 유형 토글이 주택 유형 칩과 충돌해 필터 상태가 오염되거나 지도/카드 수가 불일치한다.
6. 서비스키/금전 입력이 클라이언트에 노출되거나 rent API 요청에 재무 값이 포함된다.
